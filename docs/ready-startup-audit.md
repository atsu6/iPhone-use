## 归因与修正

第一条报错包含两个层次：底层 WDA / XCTest 通道确实不可用；模型又把正常任务的初次 READY 设置为 recover=false，阻止已有恢复路径执行。参数本身符合 schema，日志中的模型说明只说要先检查就绪，未给出关闭恢复的用户约束。因此不能把这次错误归为 schema 验证失败，也不能声称恢复机制没有工作；下一次允许恢复的调用已成功重启并通过真实验收。

0.1.4 的改动针对指导和状态呈现，不宣称根治 iOS / XCTest 的授权生命周期问题：

- 正常任务首次 READY 用默认 recover=true，明确区分用户要求的只读诊断 / 禁止重启；不因预检或谨慎主动关闭恢复，也不自动覆盖用户限制。
- 正常通过时返回 `ready=true, state="ready"`。后台恢复排队或运行时返回 `ready=false, state="recovering"`，继续使用既有 job / status / READY 流程。
- recover=false 下的持续通道故障返回 `ready=false, state="recovery_required", reason="recovery_disabled"`，保留 cause 和下一次调用指引；只有当前用户指令允许恢复时才继续 recover=true。
- 两种预期未就绪状态作为正常工具结果，无 error 且 MCP isError=false；实际恢复拒绝、冷却、锁屏、未知故障仍返回错误。调用方始终检查 ready / state，不把无红错、HTTP 成功或 setup 工作 running 当作 READY / 任务完成。

恢复仍保留身份、端口监听和进程组归属核验、去重、冷却和有效构建限制；旧 session / 观察作废，失败的业务动作不会自动重放。自动回归及发布验证记录见 [验证记录](validation.md)。上表的约 6.9 秒是该历史自然故障恢复的观察值，不是 0.1.4 新实测或所有设备的时间承诺。

## 同次测试的其他报错

最终审计覆盖该测试聊天至结束时刻 2026-10-07 01:31:30（中国时间；原始 rollout 的 task_complete 为 01:31:30.707）。重新读取确认聊天为 completed / idle，全部 548 条原始事件中仍共出现 11 次 WDA MCP 错误返回，覆盖以下 7 类，另有 1 次非插件 shell 错误；此前快照之后没有新增报错，没有本次 schema `invalid_argument` 记录。每条错误的作用层和处理方法不同，不能通过删除检查把它们统一变成操作成功。以下只记录通道和通用交互证据，不改变用户要求暂缓的账户分栏业务规则。

| 类别 / 次数 | 可确认的原因和执行边界 | 0.1.4 的处理与保留边界 |
| --- | --- | --- |
| `wda_recovery_required` ×1 | 首次 READY 显式 recover=false，持续失效前台未被恢复；未执行手机业务动作。 | 正常诊断状态 recovery_required / recovery_disabled，按用户约束决定是否允许恢复。 |

富途面板在背景点击检查失败前就已存在。随后无进展滚动没有解决遮挡；后来基于新观察的面板外点击移除面板，重新定位的背景点击才通过。这里改善的是通用浮层识别与执行边界指导，不把特定 App 的固定坐标或账户选择流程写成插件规则。没有原生 modal 节点也不能证明没有浮层；新增加的原生浮层检查不能保证识别所有自定义面板。

招行无进展前后截图中的主要内容位置相同，仅滚动指示条的显示变化，不支持“工具漏掉了实际内容滚动”的结论；同时截图仍有截断内容，不能据无进展证明已经到达业务终点。两个招行 stale 的真实中间状态未保存在工具结果中，归因应保留该证据限制。

另有 1 次非插件 shell 错误：临时脚本放在 `/tmp`，Node 无法解析 `@oai/artifact-tool`（`ERR_MODULE_NOT_FOUND`）。测试聊天将脚本放到具有依赖路径的项目输出目录后继续；这是评测表读取脚本的模块查找问题，和 WDA 通道、schema、手机控件无关。

新增回归检查的是这些通用保护、诊断和短转场行为，不能据合成测试宣称已重跑上述金融页面。此审计未对测试聊天或手机执行操作。
