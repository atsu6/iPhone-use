# T01 中途结束调查

本次调查只读取测试会话、Codex rollout、桌面日志及插件源码，没有重跑手机任务。日志记录的测试模型为 `deepseek/deepseek-v4.1-flash`，推理级别为 `high`。Codex 的 provider 配置标识是 `openai`；这个标识不能用来把该模型解释为 GPT，也不能据此确认底层请求直接发往哪个 API 地址。

## 能确认的结论

三次中途结束都被记录成助手 `phase=final_answer`，随后出现 `task_complete`。最终文本仍在描述下一阶段工作，而用户要求的交付尚未全部完成。用户继续后，同一模型可以接着操作工具并完成剩余工作。

工具错误增加了绕路和耗时，但不是这三次结束的必要触发条件：第二、第三次结束前最后的 WDA 调用均成功，`isError=false`，滚动结果为 `action_executed=true`、`verified=true`、`changed=true`。没有观察到工具协议解析失败、WDA MCP 进程崩溃、模型上下文超限或这三次回合被用户中断的记录。

因此，目前证据最支持**模型 / Codex 运行时的继续执行与结束回合判断出现问题**。插件结果并没有要求结束整个任务。现有日志不包含原始 API `finish_reason` 或 provider 响应流，无法进一步证明究竟是模型主动发出停止、provider 适配层的行为，还是文本阶段映射导致；不能把这一点写成已经证实的 DeepSeek 模型缺陷。

## 返回格式和上下文负担

插件的 `result_content()` 返回 MCP 的 `content`、`structuredContent` 和 `isError`；`serve()` 把业务错误放在工具结果中，仍保持 JSON-RPC 响应格式。错误带有明确错误码，成功滚动结果也明确区分动作执行和局部变化验证。[MCP Tools 规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools) 将 `isError` 定义为工具执行错误状态；它不是整个用户任务的完成信号。

本次成功动作有时仍包含 `verified=false` 或 `verification_required`，这表示尚需检查页面 / 业务后置条件。代理应补验该条件，不能据此默认整个任务已完成，也不能把正常的补验标记当作不可恢复的 MCP 故障。

首个模型响应前，记录的输入已达 476,544 tokens。三次结束响应的输入分别是 663,222、724,661、739,652 tokens；最终完成响应是 825,134 tokens。记录的模型上下文窗口为 996,147 tokens，未发现 compaction 或超限事件。累计 `total_token_usage` 包含多次请求，不能拿它与上下文窗口直接比较。

这是很大的上下文负担，可能增加延迟和偏离任务的概率，但本次没有对照实验，不能据此证明提前结束的原因。尤其首个响应尚未取得本次手机观察，已有的大输入不能全部归因于本插件的返回值。读取截图时日志还记录了后续 `view_image`，因此可优先利用 MCP 已附带的图像，避免重复观察和额外回合。

## 插件可以采取的措施

1. 开始任务时把用户要求拆成可核验的交付项；分别维护已完成、待完成和真正受阻的范围。单个工具成功和一个 App 阶段结束都不能满足全部完成条件。
2. 进度说明使用 commentary，并在同一回合继续下一步工具调用。只要还能够安全推进，就不要把“接下来开始……”作为最终回答。
3. 最终回答前核对所有交付项、关键字段 / 覆盖范围及输出文件的实际写入结果。必要的用户接管或不可恢复限制可以结束回合，但必须明确已完成和剩余范围。
4. 工具失败时执行一次有针对性的恢复：新观察、修正定位或使用已授权的直接 WDA 调用。保持失败和不确定写入的边界，不能为了避免中断而无限重试或自动重放提交。
5. 使用紧凑观察、明确后置条件和已知路径批量操作减少模型回合。长任务保存检查点；恢复时从最后的已验证状态继续。

这些措施是给代理的执行规则，不能保证某个模型永远不会提前结束。MCP 服务无法在 Codex 已接受最终回答后自行恢复回合。若仍复现，需要以最小任务、较精简的工具 / 上下文配置、相同输入和其他模型作对照，并由 Codex / provider 侧保留原始完成原因，才能进一步归因。

原始会话标识、金融内容和日志摘录仅保留在用户本机的私有验证目录，不提交到此仓库。本文件只保留通用错误类别、工具状态、时序及调查限制。
